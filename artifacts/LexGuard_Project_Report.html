1. Executive Summary

LexGuard is a full-stack AI-powered legal contract intelligence platform built specifically for Indian jurisprudence. It allows users to upload employment contracts, SaaS agreements, freelance contracts, and other legal documents, and automatically:

  • Parses the document (PDF/DOCX) into individual clause segments
  • Classifies each clause into 17 legal categories using an AI agent
  • Assesses risk on a 4-tier severity scale (LOW → MEDIUM → HIGH → CRITICAL) using a multi-agent adversarial pipeline
  • Maps violations to specific Indian statutes (Contract Act 1872, DPDP Act 2023, Copyright Act 1957, etc.)
  • Generates plain-language explanations for non-lawyers with negotiation tips and suggested rewrites
  • Runs statutory compliance checks against a 7,500+ node legal knowledge base
  • Provides an interactive AI chat (Agent 5) for asking questions about the uploaded contract

The system operates on a freemium SaaS model with Razorpay payment integration and a 3-tier pricing structure (Free / Pro / Enterprise).

LexGuard follows a modular, multi-agent architecture with graceful degradation at every layer. The system is designed so that no single point of failure can bring down the entire pipeline.

Core Design Principles

  • Multi-Agent Architecture: Each AI agent is a specialized, isolated module with its own system prompt, temperature setting, and output schema
  • Dual-Layer Defense (V8): LLM Asymmetry analysis (Commercial intelligence) + Deterministic keyword traps (18 patterns)
  • Adversarial Verification: Every risk assessment is cross-examined by a hostile "Judge" agent before finalization
  • Serverless Resilience (GridFS & Redis): Zero third-party upload dependencies. Uses Native Mongoose GridFS memory streaming to completely prevent BSONVersion mismatch errors and robust rediss:// strict URL parsing for Upstash serverless caching.
  • Deterministic Mapping: Perfect data integrity via segmentIndex sorting instead of unpredictable MongoDB ObjectId string matching.
  • Graceful Degradation: Redis → MongoDB fallback for queuing; LlamaParse → pdf-parse → Tesseract OCR fallback for parsing
  • Vector Grounded Compliance: 384-dimensional database-native $vectorSearch with a rigid 0.82 threshold.

5. The 6-Agent AI Pipeline

The heart of LexGuard is a sequential multi-agent pipeline orchestrated by jobQueueService.js. When a contract is uploaded, the following agents execute in strict order:

graph LR Upload["📄 Upload"] --> Parse["🔧 Parse & Split"] Parse --> A0["🧠 Agent 0\nPreFlight"] A0 --> A1["📋 Agent 1\nClassifier"] A1 --> A2["⚠️ Agent 2\nRisk Analyst"] A2 --> A25["⚖️ Agent 2.5\nAdversarial Judge"] A25 --> V6["🛡️ V6 Traps\n18 Patterns"] V6 --> A3["💬 Agent 3\nUser Advocate"] V6 --> A4["📜 Agent 4\nCompliance"] V6 --> EMB["🔢 Embeddings"] A3 --> Done["✅ Complete"] A4 --> Done EMB --> Done

Figure 2: The 6-Agent AI Pipeline — From Upload to Complete Analysis

5.1 Document Parsing & Clause Splitting

The parser implements a 3-tier fallback chain:

  • LlamaParse (cloud-based, highest fidelity) → falls back to:
  • pdf-parse (local Node.js library) → falls back to:
  • Tesseract OCR (for scanned/image-based PDFs)

The clause splitter is a pure heuristic, zero-AI module that splits on double newlines, numbered/lettered sub-items, merges orphan segments under 30 characters, and filters out too-short segments.

5.2 Agent 0 — PreFlight Global Context Extractor

Purpose: Scans the first 12,000 characters to extract governing law, employer name, employee designation, and global definitions. This context is injected into every subsequent agent call.

Temperature: 0.1  |  Max Tokens: 1,500

5.3 Agent 1 — Clause Extractor & Classifier

Purpose: Classifies each clause into one of 17 legal categories. Key design decisions include explicitly separating confidentiality from privacy_data, forcing Garden Leave into termination, and placing liquidated damages under compensation.

Temperature: 0.1  |  Batch Size: 10 clauses per API call

5.4 Agent 2 — Risk Analyst

Purpose: The most complex agent. Evaluates each clause for risk severity and maps it to Indian statutes. Contains Safe Harbor Validation Protocol, Precedent Prioritization Protocol, Persona Filtering, and Dynamic Citation Subtitles.

Temperature: 0.2  |  Max Tokens: 6,144

5.5 Agent 2.5 — Adversarial Judge

Purpose: An adversarial quality-control layer that audits Agent 2's output for False Positives (over-flagging safe clauses) and False Negatives (missing predatory traps). The Section 27 Exception: a non-compete during active employment is valid (LOW), but post-employment non-competes are void (CRITICAL).

Temperature: 0.1 (deterministic)

5.6 Agent 3 — User Advocate

Purpose: Generates plain-language explanations, worst-case scenarios, negotiation tips, and suggested rewrites for medium/high/critical-risk clauses. LOW-risk clauses are skipped entirely.

Temperature: 0.25  |  Max Tokens: 4,096

5.7 Agent 4 — Indian Compliance Checker

Purpose: The final statutory cross-examination pass. Uses the LegalDomainMap ontology to route clauses to relevant legal domains, then runs Atlas Vector Search to find matching statutes, and injects them into the LLM prompt for compliance analysis.

Temperature: 0.0 (absolute determinism)

5.8 Agent 5 — Contract Chat

Purpose: Interactive Q&A interface using RAG. Generates an embedding for the user's question, performs vector search against clause embeddings, and injects the top 5 relevant clauses as context.

Temperature: 0.3

6. V8 Asymmetry Engine & Deterministic Safety Net

The mathematically secure guardrail that runs AFTER the LLM and Judge. It combines an advanced Asymmetry Engine with pure keyword pattern matching (no AI) to catch predatory traps that LLMs consistently under-rate.

7. RAG Pipeline

The RAG (Retrieval-Augmented Generation) pipeline ensures Agent 4's compliance checks are grounded in real statutory text, not hallucinated legal knowledge:

  1. Ontology Routing: LegalDomainMap maps (contractType, clauseType) → legal domains
  2. Vector Grounding: Clause text is embedded using all-MiniLM-L6-v2, then executed as a native $vectorSearch aggregation directly in MongoDB.
  3. Semantic Relevance Threshold: Results are strictly filtered through a 0.82 cosine similarity threshold.
  4. Domain Filtering: Only statutes in the routed domains are returned (zero cross-contamination)
  5. Prompt Injection: Top 3 matching statutory sections are injected into Agent 4's system prompt

Figure 4: End-to-End User Journey — From Signup to Contract Analysis

Detailed Upload-to-Result Flow

  1. User uploads a .pdf or .docx file with a selected category
  2. Multer validates file type, enforces 10MB limit, and buffers to memory
  3. Native GridFS Pipeline streams the buffer directly into the Mongoose connection without unstable third-party wrappers, guaranteeing 100% BSON version compatibility
  4. ParserService extracts raw text (LlamaParse → pdf-parse → OCR fallback)
  5. ClauseSplitter breaks text into individual clause segments (pure heuristic)
  6. Contract and Clause documents are persisted to MongoDB
  7. JobQueueService enqueues the contract (Redis or MongoDB)
  8. Background Worker picks up the job and executes all 6 agents sequentially
  9. Contract status transitions to done with computed overallRiskLevel
  10. Frontend polls for job completion, then renders the full analysis
